# whyline-relay 0.2.18

Grok's structured headless result is now understood well enough to distinguish a cancelled turn from a real quota signal. A denied Grok command pauses with an actionable permission-policy message instead of being mislabelled as rate-limited or silently switching to a backup.

## What changed

- **Structured Grok cancellation handling.** A generic agent whose executable is `grok` is inspected for `stopReason: "cancelled"`. The relay reports that Grok's headless permission policy likely cancelled the turn and points to the configured `--allow` rules. Grok remains a generic agent: the relay still cannot name the denied command that Grok omitted or verify its login non-interactively.
- **No routing from private reasoning.** Grok's `thought` field is excluded from rate-limit detection. Task prose mentioning “usage limit” or “rate limit” can no longer trigger a false backup switch after a permission cancellation.
- **Conservative cancellation semantics.** A cancelled Grok result is never treated as quota evidence. A non-cancelled result can still report a genuine usage limit through its final `text`, `message`, or `error` field.
- **Correct pretty-printed JSON extraction.** Generic response extraction now understands a complete multi-line JSON object as well as the existing compact final-line format. Chat therefore returns Grok's actual `text` instead of the closing `}` from pretty-printed output.
- **Truthful chat status.** A structured Grok cancellation is recorded as a failed chat turn even when the Grok CLI itself exits with status zero.

## How it was checked

- Regression coverage reproduces the exact failure mode: a cancelled Grok result whose private reasoning repeats “usage limit” is not classified as rate-limited and produces a permission-policy diagnostic.
- The fix was also run directly against the historical CF-5 Grok log that caused the false pause: `rate_limited=False`, `cancelled=True`.
- The complete suite passes with 579 tests.

## Remaining limitation

`stopReason: "cancelled"` does not identify the denied command. Whyline can now classify and explain the stop safely, but the Grok CLI must expose richer denial metadata before Whyline can tell the user exactly which `--allow` rule is missing.

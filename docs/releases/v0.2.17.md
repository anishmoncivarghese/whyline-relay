# whyline-relay 0.2.17

Chat can now switch automatically to a configured backup when the agent you address hits a detected usage limit or is no longer authenticated. The retry is immediate, sticky for later turns, and deliberately limited to one hop.

## What's new

- **Per-agent chat backups.** Configure `[chat.backup]` independently from the task pipeline's role backups. Built-in agents work by name, and configured generic agents can be backup targets.
- **Automatic one-hop retry.** When a requested agent hits a detected rate limit or authentication loss, chat records the override and reruns the same prompt once on its backup. If that backup also fails, chat reports the failure and stops rather than chasing another agent.
- **Sticky but explicit state.** Active chat overrides live in `.whyline/relay/chat-active-agents.json`, separate from pipeline role overrides. The saved default agent is never rewritten.
- **New `/backups` and `/reset-backup [agent]` commands.** The REPL shows active switches and can clear one or all of them. Failover notices are printed before the backup's response.
- **Backward-compatible failover storage.** The existing pipeline-side failover APIs retain their original defaults; the optional storage path is used only when chat needs its separate namespace.

## How it was checked

- Focused coverage for failover storage, chat backup configuration, automatic retry, one-hop stopping, sticky resolution, REPL notices, and reset commands.
- The complete test suite passed on the release tree before tagging.
- Built by running whyline-relay on its own five-task plan with Grok implementing and Codex reviewing.

## Known issue

Grok remains a generic agent. Its CLI reports a denied headless action only as `stopReason: "cancelled"`, and arbitrary task text can contain the same phrases used by the relay's legacy text-marker rate-limit detector. During this release's own documentation task that combination produced a false rate-limit pause after the actual edit and tests had completed. It did not affect the shipped chat failover behavior; structured Grok cancellation handling is planned as a separate follow-up.

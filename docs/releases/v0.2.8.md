# whyline-relay 0.2.8

`[pipeline]` can now configure a real multi-stage graph — any number of named stages, each with its own outcome vocabulary and rejection target — in place of the fixed implementer/reviewer pair, built on 0.2.7's `pipeline.py` engine. A task paused mid-pipeline resumes at the exact stage and visit count it paused at, never re-running a stage that already finished and never silently skipping one either. Built by running whyline-relay on its own plan.

## New

- **`[pipeline]` / `[pipeline.profiles]` / `[pipeline.stages.<id>]`**, a new `config.toml` table: any number of stages, each naming a role, a prompt, and an `on` table mapping outcomes to a target stage, `"@next"` (the following stage in whichever profile is running — the same stage can mean a different "next" in different profiles), `"@complete"`, or `"@blocked"`. Every profile is checked at config-load time to have some path to `"@complete"`. See [Configuring a custom pipeline](../../README.md#configuring-a-custom-pipeline).
- **A task can pick a non-default profile** with a `relay-profile: NAME` line in its detail; `doctor` fails if the name isn't one of `[pipeline.profiles]`, and warns (doesn't fail) if it's used with no `[pipeline]` configured at all.
- **Crash-safe stage resume**: `RelayState` now additionally saves which stage a paused task was on, which profile, and how many times each stage has run, checkpointed *before* every agent launch. `resume` re-decides against whatever handoff already exists rather than blindly trusting the saved stage, so a crash between an agent's turn and the relay routing it is never double-consumed or dropped. A `[pipeline]` fingerprint (a hash of the whole table) is saved alongside the stage state; if the config changes before `resume`, the relay refuses to guess rather than replay stale visit counts against a reshaped graph.
- **Only a stage that can reach `"@complete"` may commit** — the reviewer-only commit rule generalized to whichever stage(s) a configured graph lets finish the task, HEAD-checked the same way.
- **Custom prompts get four new placeholders**: `{actor}`, `{role}`, `{stage}`, `{profile}`. A stage's `prompt` name is looked up as a user override first, a built-in (`implement`/`review`) second; naming anything else with no override file is now a `doctor` FAIL (`prompts.PromptError`), not an unhandled `KeyError` at run time.
- **`[roles.backup]` and `[pipeline]` are mutually exclusive**, and so are a hand-written `[status_map]` and `[pipeline]` — both refused with a `ConfigError` at load time. A configured pipeline has no failover: a stage with no working agent pauses.
- **`doctor` checks a configured pipeline's real agents**, not the legacy `[roles]` placeholder it silently checked before: `_agents_in_use` — and with it, the permission-bypass-flag and generic-agent warnings — now derives its agent list from `[pipeline]`'s own roles when one is configured. This closes a real gap: before this release, those checks always inspected `settings.roles.implementer`/`.reviewer`, which mean nothing once `[pipeline]` is set, so a pipeline's actual agents went completely unchecked.

## Who this affects

Nobody without a `[pipeline]` table. Every existing test — including the entire prior acceptance suite, run unedited — passes unchanged; `_run_task`'s legacy code path was touched only for a 3-argument `on_turn` callback and some new optional, defaulted parameters on `_run_agent`, neither observable without a configured pipeline.

## Upgrading from 0.2.7

`uv tool upgrade whyline-relay`. Nothing to do unless you want `[pipeline]`; write it by hand (there is no `init`/`roles set` wizard for it yet) matching the shape in the README.

## How it was checked

- 409 tests (378 before).
- The full prior acceptance suite (192 relevant tests across every earlier release, plus the 7 from 0.2.7's `pipeline.py` groundwork) run unedited against the result — zero regressions. One 0.2.7-era acceptance test pinning `[pipeline]` as "silently ignored, not built yet" now correctly fails, since that's exactly what this release replaces; it is retired, not fixed.
- 5 new independent acceptance tests, written and validated against a hand-built reference implementation of this plan *before* it was ever handed to Codex — a genuine end-to-end 3-stage run, `doctor` catching an unresolvable stage prompt, `relay-profile:` picking a shorter profile (proving `"@next"` resolves against the right profile, not a fixed compiled graph), and a real crash-then-resume that proves the already-finished stage is never re-run.
- The two riskiest design calls — `pipeline.decide()`'s stage-and-profile-aware routing, and the crash-safe checkpoint-before-launch resume semantics (including the per-stage visit cap standing in for any static "unbounded cycle" check, and the fingerprint drift check) — were built and proven correct in a scratch copy against real handoff records before a line of the plan was written, the same discipline as 0.2.6 and 0.2.7.

## Known issues

Same as 0.2.7, minus what this release fixes, plus: no `init`/`roles set` wizard for authoring `[pipeline]` yet (write it by hand); no built-in tester/security-review prompt content (a stage naming one must supply its own `.whyline/relay/prompts/<name>.md`, which `doctor` now enforces); relay-side commit ownership (a configured pipeline's agents still run `git commit` themselves) is a separate, later piece of the same design (`docs/superpowers/specs/2026-09-23-relay-n-roles-design.md`).

# whyline-relay 0.2.12

`whyline-relay init`, run genuinely interactively (no `--yes`), now asks about each role's agent and, for a built-in, its model — the same wizard `roles set` already gave you for changing a role later, now available at setup time too. `--yes` and explicit `--implementer`/`--reviewer` flags are completely unaffected. Built by running whyline-relay on its own plan.

## New

- **`init` asks "Implementer agent [codex]:" and "Reviewer agent [claude]:"** when run interactively with no `--implementer`/`--reviewer` flag for that role. A blank answer keeps the default; an answer that isn't a built-in agent name is refused cleanly, with nothing written.
- **`init` then asks "Model for `<agent>` (blank for default):"** for every agent actually in use — including when the agent was already given via flag, since there has never been a flag for model selection at `init` time. A chosen model is written as `[agents.<name>] model = "..."`, the same shape `roles set --model` and 0.2.6's model selection already produce.
- **`--yes` is untouched.** Every scripted or CI `whyline-relay init --yes` (including every sandbox this project's own relay-driven releases use) produces exactly what it always has — verified with a `confirm` that raises if called at all.

## Who this affects

Nobody who runs `init --yes` or supplies both `--implementer` and `--reviewer`. A plain, non-`--yes` `init` in a real terminal now asks a few more questions than before finishing with the existing "Write these? [Y/n]" confirmation.

## Upgrading from 0.2.11

`uv tool upgrade whyline-relay`. Nothing to do.

## How it was checked

- 443 tests (438 before).
- The full acceptance battery re-run unedited: 213 relevant tests pass, the only two non-passes being an out-of-scope suite and one pre-existing baseline failure already confirmed to fail identically on unmodified 0.2.11.
- 6 new independent acceptance tests, written and validated against a hand-built reference implementation *before* this plan was ever handed to Codex, using piped stdin the way a real terminal session supplies answers: the chosen agents and model landing in `config.toml`, blank answers keeping every default, an unknown agent name refused cleanly, an explicit `--implementer`/`--reviewer` flag skipping only its own agent question (never the model one), and a fully non-interactive invocation (piped from `/dev/null`) still aborting safely.
- The two subtlest correctness properties were proven directly in a scratch copy before a line of the plan was written: `assume_yes=True` never calls `confirm` under any circumstance, and an EOF on any of the new questions (no terminal at all) falls back to a default rather than aborting immediately — the existing final "Write these?" question's own pre-existing EOF handling is what actually aborts the run, unchanged.
- The run itself completed with zero pauses.

## Known issues

Same as 0.2.11, minus what this release fixes, plus: `init` still never reads an *existing* `config.toml` — it only ever generates one from scratch or, with `--overwrite`, replaces it outright (unchanged, documented behavior). Teaching a re-run of `init` to ask about a configured `[pipeline]`'s own roles, rather than only the legacy pair, is a separate, later piece.

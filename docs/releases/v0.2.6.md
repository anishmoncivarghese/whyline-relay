# whyline-relay 0.2.6

A named agent can now alias a built-in adapter (`codex` or `claude`) with its own command and model, so `claude-opus` and `claude-haiku` can each fill a different role, both fully managed, instead of one of them having to fall back to an unmanaged `generic` agent just to pick a different model. Built by running whyline-relay on its own plan.

## New

- **A custom agent name may declare `adapter = "codex"` or `adapter = "claude"`**, not only `"generic"`. It gets that adapter's full managed behaviour — login check, permission-bypass refusal, denial parsing — under its own name, with its own optional `command` override.
- **`model`**, an optional key on any `[agents.*]` table naming a built-in adapter (aliased or literal), turned into the tool's own real flag: confirmed against actual `--help` output, `codex exec -m/--model <MODEL>` and `claude --model <model>` (accepting an alias like `opus`/`sonnet`/`haiku`/`fable` or a full model name). `[agents.claude] model = "haiku"` works directly on the literal name too, with no alias needed.
- A `generic` agent cannot take `model` — there is nowhere for the relay to put it. Put the flag directly in `command`, as always.

## Who this affects

Nothing changes for a `config.toml` with no `model` key and no non-`generic` `adapter` on a custom name — every message, file, and default is exactly what 0.2.5 produced.

## Upgrading from 0.2.5

`uv tool upgrade whyline-relay`. Add `adapter`/`model` to a custom agent's table, or `model` to `codex`/`claude` directly, whenever you want it.

## How it was checked

- 362 tests (349 before).
- 167 existing acceptance tests (97, 53, and 17 from earlier releases), run unedited against the result.
- 11 new independent acceptance tests, written from the plan's requirements before the run and validated against a scratch copy of the actual planned code change before it was ever handed to an implementer: every `[agents.*]` validation error; a custom name aliasing `claude` is login-checked and bypass-checked as the real `claude`, by its real binary, not its registry name; `doctor` and `--dry-run` show the model flag; a `generic` agent is completely unaffected; a real run with a model-variant implementer completes and the process actually receives `--model <name>`.
- No model string is checked against what an account can actually use — an unavailable model fails at run time, the same as any other agent failure. This is deliberate, not an oversight: none of the three tools has been measured to report what an account can use.

## Known issues

Same as 0.2.5, plus: model availability is unmeasured (see above).

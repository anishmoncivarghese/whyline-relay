# whyline-relay 0.2.10

Two new built-in prompts — `test` and `security` — ship real, usable content for a `[pipeline]` stage naming either one, no override file required. Making that possible required the other half of this release: every configured-pipeline stage's rendered prompt now gets a relay-generated routing footer stating the exact permitted outcomes, the exact agent to address each one to, and the literal `whyline handoff` command to run — so a built-in or custom prompt's own text never has to hardcode a specific pipeline's outcome vocabulary or guess which agent currently fills the next stage's role. Built by running whyline-relay on its own plan.

## New

- **`test` and `security` are built-in prompt templates**, alongside `implement`/`review`. A `[pipeline.stages.*]` naming `prompt = "test"` or `prompt = "security"` now resolves with no `.whyline/relay/prompts/*.md` override needed — `doctor` used to fail this with `PromptError`; it now accepts it outright. `test` reviews for genuine test coverage (not tautological assertions) and may add real tests itself, but never touches the implementation. `security` checks for injected input, leaked secrets, and over-broad permissions, and is explicitly not a second correctness pass. Both are profile-gated like any other stage — a profile either lists `"test"`/`"security"` among its stages, or doesn't.
- **`prompts.stage_footer()`**, appended to every configured-pipeline stage's prompt at render time: resolves each of the stage's transitions (including a profile-relative `"@next"`, exactly the way `pipeline.decide()` already does) into the literal recipient and a ready-to-run `whyline handoff` command. A hand-edited, stale prompt can still describe the task wrong; it can no longer send a handoff to the wrong place, because the routing text is generated fresh every turn from the pipeline actually configured right now.
- The footer also carries the "do not commit" notice a configured pipeline's stages have needed since 0.2.9's relay-side commit ownership — piece C's ad hoc `NO_COMMIT_NOTICE` constant is retired in favor of this fuller, stage-aware footer.

## Who this affects

Nobody without a `[pipeline]` table. Legacy `implement.md`/`review.md` and their `{implementer}`/`{reviewer}` placeholders are completely unchanged and never gain a footer.

## Upgrading from 0.2.9

`uv tool upgrade whyline-relay`. If you already wrote your own override for a `test` or `security` stage prompt, it still takes precedence over the new built-ins — nothing to change. If you were relying on `doctor` rejecting an unconfigured `test`/`security` stage prompt, it no longer will; give the stage a different name if you actually meant to write your own content.

## How it was checked

- 421 tests (415 before).
- The full acceptance battery re-run unedited: 198 relevant tests pass, the only two non-passes being an out-of-scope suite and one pre-existing baseline failure already confirmed to fail identically on unmodified 0.2.9. Two more 0.2.8/0.2.9-era acceptance tests that pinned `"test"` as an unresolvable prompt name are updated to name a genuinely unresolvable one instead — that pin is exactly what this release replaces.
- 5 new independent acceptance tests, written and validated against a hand-built reference implementation *before* this plan was ever handed to Codex: `doctor` accepting the built-in `test` prompt with zero override files, a full pipeline run completing on that built-in content alone, the routing footer's literal handoff commands showing up in a real turn's log, and a `security` stage present in one profile and cleanly absent from another.
- The footer's own correctness (profile-relative `"@next"` resolution, `"@complete"`/`"@blocked"` handling, per-outcome recipients) was proven directly against real `Pipeline`/`Profile` values in a scratch copy before a line of the plan was written — the same discipline as every release since 0.2.6.

## Known issues

Same as 0.2.9, minus what this release fixes, plus: the fuller structural protocol footer envisioned in the N-roles design's prompts section (a fully generated body, not a plain-text block appended after the editable template) is still a later refinement — this release ships the routing information that piece actually needed. `init`/`roles set` support for choosing a tester or security-review stage when setting up a pipeline interactively is a separate, later piece (`docs/superpowers/specs/2026-09-23-relay-n-roles-design.md`, D11).

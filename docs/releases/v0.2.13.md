# whyline-relay 0.2.13

`whyline-relay plan "<description>"` drafts a `plan.md` for you instead of you writing one by hand: an agent drafts, a second agent checks the draft's structure only (never whether it's the right plan — that stays your call), and you get a three-way gate — approve, request changes, or discard — with an offer to start the real run immediately once you approve. This completes the N-roles design's last deferred piece ("the planner"). Built by running whyline-relay on its own plan, exactly like every piece since 0.2.8.

## New

- **`whyline-relay plan "<description>"`** runs an unattended draft↔structural-review loop (`[planner].draft`/`[planner].review`, defaulting to your existing implementer/reviewer agents) and stops for you once it converges, showing the full draft.
- **The human gate**: approve (writes and commits the real `plan.md`, then offers to run `whyline-relay start` on it immediately), request changes (redraft with your feedback — unbounded, since you're driving it), or discard.
- **`[planner]` config**, entirely optional:
  ```toml
  [planner]
  draft = "codex"     # defaults to your implementer's agent
  review = "claude"   # defaults to your reviewer's agent
  max_visits = 3       # bounds only the unattended draft<->review loop
  ```
- **Full crash-safe resume**, via a new, separate checkpoint (`plan-state.json`) that never touches `RelayState`'s task/git-shaped fields: an interrupted draft/review turn, or an unanswered approval gate, picks back up exactly where it left off via the existing `whyline-relay resume` command. `whyline-relay plan --discard` abandons an in-flight session without resuming it.
- **`doctor` warns** if a real plan task ever uses the id `__plan__` — the planner's own reserved handoff id.

## Who this affects

Nobody who doesn't run `whyline-relay plan`. Every other command is unaffected; `resume` gained one new dispatch branch that only triggers when a plan checkpoint exists, which no prior workflow ever produces.

## Upgrading from 0.2.12

`uv tool upgrade whyline-relay`. Nothing to do — `[planner]` is entirely optional and defaults sensibly from your existing `[roles]`.

## How it was checked

- 473 tests (443 before).
- Every task was independently rebuilt in a throwaway probe *before* this plan was ever handed to Codex, catching four real bugs empirically: the draft/review prompt templates used `## Description` instead of `## Task {task_id}`, which was both inconsistent with every other built-in template *and* broke task-id extraction in the shared test fixture; neither template referenced `{actor}`/`{role}` at all, missing the `whyline note` decision-recording line every other built-in prompt has; a test helper built a fresh scripted-response list inside its mock on every call instead of once outside it, silently replaying the first response every turn; and `plan --discard` didn't check for a live relay before touching the checkpoint.
- The real run itself completed all 9 tasks with exactly one pause: the reviewer tried a piped test command and was denied permission — the `REVIEW` prompt already explicitly warns against this; not a code defect, resolved by resuming with `--allow-dirty` since the working tree only held the implementer's own legitimate in-progress work.
- The cherry-picked tree was diff-verified byte-for-byte against the sandbox (excluding gitignored runtime state) before merging.
- The full flow was verified twice as a genuine subprocess — real fake `codex`/`claude` executables on `PATH`, the real `whyline` CLI, not a simulation — once against a hand-built reference implementation and again against the actual merged code: draft → structural review → approval gate → `plan.md` written and committed → declined to start. Confirmed against the unmodified 0.2.12 baseline that `plan` isn't even a recognized subcommand there, so none of this was already accidentally working.

## Known issues

None new. `[roles.backup]` interactions with a configured `[pipeline]` remain as previously documented; the planner does not (yet) interact with `[pipeline]`-style multi-stage task pipelines beyond sharing the same underlying `pipeline.py` engine.
